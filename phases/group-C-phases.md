# Phase 3.8 — Cart Schema

## Purpose

Implement the database foundation for customer and guest shopping carts.

The Cart model must explicitly support two ownership modes:

```text
AUTHENTICATED CUSTOMER
ANONYMOUS GUEST
```

A Cart must belong to either:

```text
an authenticated customer
```

or:

```text
an anonymous guest represented by a secure guest-cart bearer credential
```

but never both simultaneously.

The persisted database value for a guest credential is **not the raw credential**. The database stores:

```text
guest_token_digest
```

while the client holds the raw:

```text
guest_token
```

The Cart schema must support the later:

* create/get cart flow;
* guest cart persistence;
* customer cart persistence;
* guest-to-customer cart handoff/merge;
* cart items;
* quantity updates;
* variant selection;
* stock revalidation;
* price revalidation;
* checkout;
* cart expiration/inactivation.

This phase establishes the Cart and ownership model.

Do not implement Cart API operations, Cart Item mutations, checkout, inventory reservation, or guest-cart merge behavior yet.

# 3.8.1 Cart ownership model

A Cart has exactly one ownership context.

### Customer cart

```text
cart.user_id = authenticated customer's User ID
cart.guest_token_digest = null
```

### Guest cart

```text
cart.user_id = null
cart.guest_token_digest = digest of the secure guest-cart credential
```

The two ownership modes are mutually exclusive.

Never create:

```text
user_id != null
guest_token_digest != null
```

for the same active Cart.

Do not create a third owner model.

Do not introduce:

```text
staff cart
admin cart
shared cart
anonymous user account
```

in V1.

---

# 3.8.2 Raw credential vs stored digest

Keep these concepts explicitly separate.

### `guest_token`

The raw bearer credential:

* generated by the server;
* held by the guest client;
* presented when accessing the guest Cart;
* never persisted in plaintext;
* never logged;
* never exposed through unrelated responses.

### `guest_token_digest`

The server-side database lookup value:

* deterministically derived from the raw `guest_token`;
* stored in `carts`;
* indexed/unique;
* never sent to the client;
* never treated as the guest credential.

Use the terminology consistently.

Do not replace all references to `guest_token` with `guest_token_digest`.

The raw credential remains `guest_token`; only the persisted database field is `guest_token_digest`.

---

# 3.8.3 Guest token generation

Generate the raw `guest_token` using a cryptographically secure random generator.

Use at least:

```text
256 bits of entropy
```

The token must be:

* opaque;
* unique;
* unpredictable;
* server-generated;
* non-sequential;
* independent of Cart ID;
* independent of User ID;
* independent of email;
* independent of phone;
* independent of timestamps.

Do not generate it from:

```text
cart_id
user_id
email
phone
timestamp
incrementing sequence
```

Do not use a predictable UUID construction.

Do not log the raw credential.

---

# 3.8.4 Guest token storage

**Resolved decision: use server-side digest storage.**

Store the guest credential as:

```text
guest_token_digest
```

rather than storing the raw `guest_token`.

Derive the digest using a keyed SHA-256 HMAC:

```text
raw guest_token
        ↓
HMAC-SHA-256(server secret/key, guest_token)
        ↓
guest_token_digest
```

The secret/key must be managed through the application's existing secure secret configuration and must not be stored in the database.

The stored digest should be suitable for deterministic exact lookup:

```text
WHERE guest_token_digest = ?
```

Prefer a fixed-length representation such as hexadecimal SHA-256:

```text
CHAR(64)
```

with a unique constraint.

Do not use a password-hashing algorithm such as bcrypt or Argon2 for every guest Cart lookup.

The guest token already has high entropy, while Cart lookup requires deterministic exact matching.

Do not use an unkeyed plain SHA-256 digest when a server-keyed HMAC is available.

Do not store both:

```text
guest_token
guest_token_digest
```

in the Cart table.

The raw token exists only at the credential boundary.

# 3.8.5 Cart table

Create:

```text
carts
```

with:

```text
id
user_id
guest_token_digest
status
created_at
updated_at
```

Recommended migration:

```php
Schema::create('carts', function (Blueprint $table) {
    $table->id();

    $table->foreignId('user_id')
        ->nullable()
        ->constrained('users')
        ->nullOnDelete();

    $table->char('guest_token_digest', 64)
        ->nullable()
        ->unique();

    $table->string('status')->default('ACTIVE');

    $table->timestamps();

    $table->index(['user_id', 'status']);
    $table->index(['status', 'updated_at']);
});
```

Adapt the exact migration syntax to existing Laravel/database conventions.

Do not blindly reproduce indexes that are already provided by unique/foreign-key definitions.

Do not add an index for the raw `guest_token`, because it must not be persisted.

# 3.8.6 Customer ownership

For an authenticated Cart:

```text
user_id
```

references the owning `users` row.

The owner must ultimately be an authenticated `CUSTOMER`.

The database preserves the relationship to `users`.

The actual role check belongs to the application/authorization layer.

Do not add:

```text
customer_id
```

because Customer is represented by the shared User identity.

Do not create a separate customer ownership table.

---

# 3.8.7 Guest ownership

For a guest Cart:

```text
user_id = null
guest_token_digest != null
```

The digest represents the server-side lookup identity for the raw guest credential.

The guest credential itself remains outside the database.

Do not expose:

```text
guest_token_digest
```

through the public Cart API.

Do not treat the digest as an interchangeable representation of the raw credential.

---

# 3.8.8 Guest token lookup flow

The future guest Cart lookup must follow:

```text
client presents raw guest_token
        ↓
server receives credential
        ↓
server derives HMAC digest
        ↓
lookup carts.guest_token_digest
        ↓
matching guest Cart
```

Do not perform:

```text
client guest_token
→ direct database comparison against a plaintext token column
```

because the raw token is not persisted.

Do not expose the derived digest to the client.

Do not store the raw token in request/application logs.

---

# 3.8.9 Guest token uniqueness

Every guest Cart credential must produce a unique `guest_token_digest`.

Enforce uniqueness at the database level:

```text
UNIQUE(guest_token_digest)
```

Do not rely only on random generation.

Database uniqueness remains the final defensive boundary.

---

# 3.8.10 Customer cart uniqueness

V1 should support at most one active Cart per authenticated customer.

The logical invariant is:

```text
CUSTOMER
→ maximum one ACTIVE cart
```

Do not create multiple active Carts for the same customer merely because multiple create/get requests occur.

A customer can have historical/inactive Carts.

Do not delete historical/inactive Carts merely because a newer active Cart exists.

---

# 3.8.11 Enforcing one active customer cart

The database should enforce or strongly support:

```text
one ACTIVE cart per user
```

If the target MySQL version and project conventions support an understandable generated-column/index strategy, use it.

Otherwise enforce the invariant through the application transaction and tests.

Do not create a global:

```text
UNIQUE(user_id)
```

because that would prevent historical/inactive Carts.

Do not create:

```text
UNIQUE(user_id, status)
```

because that would unnecessarily restrict future inactive status history.

The intended rule is specifically:

```text
one ACTIVE cart per customer
```

not one Cart ever.

---

# 3.8.12 Cart status

Use a CLOSED V1 status vocabulary:

```text
ACTIVE
INACTIVE
```

Do not introduce:

```text
ABANDONED
COMPLETED
CHECKED_OUT
EXPIRED
LOCKED
MERGED
```

unless explicitly approved by the API/domain contract later.

`INACTIVE` means the Cart is no longer the owner's active Cart.

Do not equate Cart status with Order status.

A Cart becoming `INACTIVE` does not by itself prove that an Order exists.

---

# 3.8.13 Guest Cart lifecycle

Guest Carts can become inactive through future operations such as:

* customer handoff;
* cart replacement;
* expiration;
* successful checkout.

Do not implement those transitions in Phase 3.8.

The schema only needs to support:

```text
ACTIVE
INACTIVE
```

without requiring destructive deletion.

---

# 3.8.14 Ownership exclusivity invariant

The primary Cart ownership invariant is:

```text
Exactly one owner context:
    user_id
    guest_token_digest
```

Valid customer Cart:

```text
user_id IS NOT NULL
guest_token_digest IS NULL
```

Valid guest Cart:

```text
user_id IS NULL
guest_token_digest IS NOT NULL
```

Invalid:

```text
user_id IS NULL
guest_token_digest IS NULL
```

Invalid:

```text
user_id IS NOT NULL
guest_token_digest IS NOT NULL
```

Implement this invariant in the application/domain layer and add a database-level CHECK constraint where safely supported by the target MySQL environment.

Do not rely solely on application code.

---

# 3.8.15 Why both owner fields are nullable

Both:

```text
user_id
guest_token_digest
```

are individually nullable because each ownership mode requires only one.

The semantic requirement is XOR:

```text
one present
one null
```

not:

```text
both required
```

and not:

```text
both optional without an invariant
```

---

# 3.8.16 No Cart ownership transfer through client input

A client must never transform:

```text
Guest Cart
```

into:

```text
Customer A Cart
```

by submitting:

```json
{
  "user_id": 123
}
```

Likewise, a customer must never claim another customer's Cart by supplying someone else's `user_id`.

Ownership transfer/handoff must be based on:

```text
authenticated principal
+
validated guest credential
```

and the later explicit handoff/merge workflow.

Do not implement handoff in this phase.

---

# 3.8.17 Cart identity vs owner identity

Keep these concepts separate:

```text
Cart.id
    = database resource identifier

User.id
    = authenticated customer identity

guest_token
    = raw guest bearer credential

guest_token_digest
    = server-side database lookup representation
```

Do not use any one as a substitute for another.

A Cart ID is not proof of ownership.

A User ID is not a guest credential.

A guest token is not an authenticated User identity.

A digest is not a client credential.

# 3.8.18 Cart items relationship

Create `cart_items` as the child schema required for Cart persistence.

Use:

```text
cart_items
├── id
├── cart_id
├── product_id
├── variant_id
├── quantity
├── created_at
└── updated_at
```

Recommended migration:

```php
Schema::create('cart_items', function (Blueprint $table) {
    $table->id();

    $table->foreignId('cart_id')
        ->constrained('carts')
        ->cascadeOnDelete();

    $table->foreignId('product_id')
        ->constrained('products')
        ->restrictOnDelete();

    $table->foreignId('variant_id')
        ->nullable()
        ->constrained('product_variants')
        ->restrictOnDelete();

    $table->unsignedInteger('quantity');

    $table->timestamps();

    $table->index(['cart_id', 'product_id']);
    $table->index(['cart_id', 'variant_id']);
});
```

Adapt the exact constraints to existing project conventions.

The Cart Item table is structural only in this phase.

Do not implement add/update/remove behavior.

# 3.8.19 Cart Item identity

A Cart Item represents:

```text
Product + Variant
```

within a specific Cart.

The existing contract defines item identity using:

```text
product_id + variant_id
```

and allows `variant_id = null` where the Product has no variant.

Do not use:

```text
product name
SKU
price
attributes
```

as the Cart Item identity.

---

# 3.8.20 Cart Item Product/Variant relationship

If:

```text
variant_id IS NOT NULL
```

then:

```text
variant.product_id === cart_item.product_id
```

must be true.

Example:

```text
Product A + Variant A
→ valid

Product A + Variant B belonging to Product B
→ invalid
```

Database foreign keys alone do not guarantee this cross-table relationship.

Enforce it at the application/domain boundary and test it.

Do not implement Cart mutation validation in this phase.

---

# 3.8.21 Cart Item quantity

Use:

```text
quantity
```

as a positive unsigned integer.

V1 maximum:

```text
100 units per Cart Item
```

The existing Cart convention defines the 100-unit line limit.

Do not store quantity as:

```text
decimal
float
string
```

Do not persist zero or negative quantities for an active Cart Item.

Deletion is handled by the later Cart API rather than representing deletion as quantity zero.

---

# 3.8.22 Cart Item uniqueness

A Cart must not contain duplicate active lines representing the same:

```text
product_id + variant_id
```

Because MySQL nullable unique columns have special semantics, do not assume:

```text
UNIQUE(cart_id, product_id, variant_id)
```

correctly handles `variant_id = NULL`.

Use a deliberate application/database strategy.

Do not create duplicate item rows merely because a client repeated an add operation.

The later Cart API will merge repeated Cart Item identity and increment quantity according to the existing contract.

---

# 3.8.23 Cart pricing

Do not persist authoritative Cart pricing.

Do not add:

```text
unit_price
subtotal
total
discount
```

to Cart or Cart Item.

The current price comes from the current Product Variant.

Authoritative checkout pricing is resolved later by the backend.

The Cart represents mutable purchase intent, not a historical financial record.

The project requires server-side financial authority and does not allow client totals/prices to become authoritative.

---

# 3.8.24 Cart Item snapshots

Do not add:

```text
product_name_snapshot
variant_name_snapshot
price_snapshot
```

to `cart_items`.

Historical snapshots belong to Order Items.

A Cart is not a historical record.

---

# 3.8.25 Inventory relationship

Do not add:

```text
stock_id
reserved_quantity
available_quantity
```

to Cart or Cart Item.

Inventory is resolved separately.

The relationship remains:

```text
Cart Item
    ↓
Product / Product Variant
    ↓

```

Inventory validation belongs to later Cart/Inventory/Checkout phases.

# 3.8.26 Cart reservation separation

Adding an item to a Cart must not reserve inventory.

A Cart represents purchase intent.

Do not add:

```text
reserved_at
reservation_expires_at
reservation_id
```

to Cart or Cart Item.

Reservation behavior belongs to later inventory/checkout design.

# 3.8.27 Guest Cart security

Treat the raw `guest_token` as a bearer credential.

It must:

* be generated server-side;
* contain at least 256 bits of entropy;
* be transmitted only through the designated guest-cart mechanism;
* never be persisted in plaintext;
* never be logged;
* never be placed in normal error messages;
* never be included in analytics;
* never be included in audit records;
* never be derived from predictable data.

The persisted:

```text
guest_token_digest
```

must also never be returned to the client.

A guest credential must never be used to access another customer's Cart.

---

# 3.8.28 Guest credential logging prohibition

Never log:

```text
guest_token
X-Guest-Cart-Id
raw guest credential
guest_token_digest
```

in:

* application logs;
* request logs;
* exception context;
* analytics;
* audit records;
* debug dumps.

Use the existing request ID mechanism for correlation without storing the credential.

---

# 3.8.29 Guest request header readiness

The later Cart API may use:

```text
X-Guest-Cart-Id
```

to carry the raw `guest_token`.

Do not create alternate V1 guest mechanisms such as:

```text
Authorization: Guest ...
guest_id
cart_token
X-Cart-Token
```

Do not implement request middleware in this phase.

The header value is the raw credential.

It is transformed into `guest_token_digest` inside the backend before database lookup.

---

# 3.8.30 Customer Cart lookup

The eventual authenticated lookup must derive:

```text
authenticated principal
        ↓
User
        ↓
ACTIVE Cart
```

using the authenticated principal.

Never use:

```text
?user_id
body.user_id
URL user_id
```

to select another customer's Cart.

The project requires server-derived identity and prohibits client identity substitution.

---

# 3.8.31 Guest Cart lookup

The eventual guest lookup must derive:

```text
raw guest_token
        ↓
HMAC digest
        ↓
guest_token_digest
        ↓
matching guest Cart
```

Do not perform database lookup using:

```text
cart_id alone
user_id
email
phone
guest_token_digest supplied by the client
```

The client supplies the raw credential, not the digest.

---

# 3.8.32 Guest-to-customer handoff readiness

The schema must support later transformation:

```text
Guest Cart
user_id = null
guest_token_digest = digest
```

into:

```text
Customer Cart
user_id = customer_id
guest_token_digest = null
```

or merging into an existing active customer Cart.

Do not implement the handoff/merge operation now.

Do not mutate Cart ownership merely because an authenticated user happens to know a guest credential.

The later operation must explicitly authenticate the customer and validate the guest credential.

---

# 3.8.33 Guest/customer merge safety

The future merge operation must prevent:

* duplicate Cart Items;
* quantity exceeding 100 per line;
* unauthorized ownership transfer;
* cross-customer access;
* item loss;
* conflicting active Carts.

The existing Cart convention requires merge identity to be based on Product + Variant.

Do not implement the merge algorithm in Phase 3.8.

# 3.8.41 Authorization separation

Cart access is ownership-based.

The future model is:

```text
CUSTOMER
→ own ACTIVE Cart

GUEST
→ valid raw guest_token

STAFF
→ no customer Cart ownership privilege merely from role

ADMIN
→ no automatic customer Cart ownership privilege merely from role
```

Role alone does not prove Cart ownership.

The project requires ownership to be checked through server-side relationships and not client-supplied identifiers.

Do not implement Cart authorization middleware in Phase 3.8.

# 3.8.50 Cart tests

Create focused tests.

## Ownership tests

Verify customer Cart:

```text
user_id != null
guest_token_digest = null
```

Verify guest Cart:

```text
user_id = null
guest_token_digest != null
```

Reject:

```text
user_id = null
guest_token_digest = null
```

Reject:

```text
user_id != null
guest_token_digest != null
```

## Guest credential tests

Verify:

* raw `guest_token` is generated server-side;
* token contains sufficient entropy;
* token is unique;
* token is not predictable from Cart ID;
* token is not derived from customer identity;
* digest is deterministic for the same token and key;
* different tokens produce different digests under normal collision assumptions;
* digest lookup retrieves the expected guest Cart;
* raw token is never persisted;
* digest is never returned to the client;
* raw token and digest are not logged.

Never put a real raw guest credential in committed fixtures.

## Customer active-Cart tests

Verify:

* one ACTIVE Cart per customer;
* repeated create/get behavior cannot produce multiple active Carts;
* inactive Cart history does not prevent creation of a new active Cart where intended.

## Status tests

Verify only:

```text
ACTIVE
INACTIVE
```

are accepted.

Unknown values are rejected.

## Cart Item tests

Verify:

* Cart relationship;
* Product relationship;
* optional Variant relationship;
* Variant/Product consistency;
* positive quantity;
* maximum quantity of 100;
* duplicate Product/Variant identity prevention strategy.

## Security tests

Verify:

* client `user_id` cannot change ownership;
* client cannot supply `guest_token_digest` as an ownership credential;
* Cart ID cannot substitute for ownership;
* raw guest token is not logged;
* digest is not logged;
* customer A cannot claim customer B's Cart;
* Staff cannot obtain customer Cart ownership through role alone;
* Admin does not automatically bypass ownership rules.

The factory must generate valid ownership combinations.

For a guest Cart:

* generate the raw token only inside the test setup boundary;
* derive its digest using the same application mechanism;
* persist only the digest.

Do not persist the raw token in the factory-created Cart.

If a test needs the raw token, expose it as a test value rather than a persisted model field.
