# API Resource Relationships — Version 1

## 0. Purpose
Authoritative catalogue of how API resources relate. Derived from frozen logical model `logical-data-model-v1.md` v1.0, `api-resource-inventory.md`, and supporting 1.6 matrices. Answers how one resource is related to, reached from, or represented alongside another before endpoint URLs are defined. No URL paths, HTTP methods, or schemas defined.

Principle: Database relationship ≠ automatically API relationship (Phase 1.7 §4). Backend is authority (AGENTS.md §3).

## 1. Legend
- **PARENT_CHILD** — child exists as part of parent; not meaningful alone.
- **OWNERSHIP** — belongs to actor for authorization.
- **REFERENCE** — refers to independent resource.
- **OPTIONAL_REFERENCE** — may not exist.
- **CONDITIONAL_REFERENCE** — required only under condition.
- **DERIVED_RELATIONSHIP** — computed for convenience, not stored as independent relation.
- **OPERATIONAL_RELATIONSHIP** — staff/admin operational.
- **INTERNAL_ONLY** — backend only, not customer-facing.

Exposure for representation (Phase 1.7 §48, aligned with `resource-embedding-policy.md`): `FULL` — complete representation embedded (`EMBEDDED` means `FULL` embedded), `SUMMARY` — small summary embedded, `REFERENCE` — identifier/link without full embed, `SUBRESOURCE` — available via dedicated subresource (not embedded by default), `INTERNAL_ONLY` (`INTERNAL ONLY`) — never exposed to customer, `LIMITED SUMMARY` — reduced summary for privacy. All `EMBEDDED`/`SUBRESOURCE` values in the catalogue map to these six.

## 3. Notes on Special Relationships
- **Cart ownership:** Guest Cart holder uses `GUEST_TOKEN` (bearer) per DM-DEC-04 / resource-access-matrix. One active Cart per holder is assumed; no multiple active carts invented. On authentication, guest Cart binds to User (IDENT-008). `Cart → User` is OWNERSHIP when authenticated, otherwise token-holder relationship.
- **Order Item historical:** Order Item must retain snapshot even if Product is archived/tombstoned; current Product reference is optional. Never let current product re-render overwrite snapshot (historical-data-rules.md).
- **Delivery conditional:** Exactly `Order → Delivery` 0..1. `PICKUP` has no Delivery; customer must not send delivery fields for pickup (CONDITIONAL_REFERENCE).
- **Status History duplication:** REL-019 and REL-020 are alternative views of same data; implementation must choose one canonical path (`tracking` includes history vs separate `status-history` subresource) to avoid duplicate mutable surfaces.
