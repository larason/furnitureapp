# Phase 1.8 — Define API Versioning

## 1. Purpose

Phase 1.8 establishes the project's **API versioning strategy** before individual endpoint contracts are created.

The objective is to ensure that the Laravel backend can evolve without unexpectedly breaking:

* the Next.js website;
* the Flutter mobile application;
* the admin application;
* future applications or integrations.

This phase defines:

* the initial API version;
* how versions are identified;
* what constitutes a breaking change;
* what constitutes a non-breaking change;
* compatibility expectations;
* deprecation rules;
* migration rules;
* client-version considerations;
* documentation/version ownership.

This phase does **not** define individual endpoints.

# 6. Versioning Principle

The API must have an explicit version from its first production release.

Do not begin implementation with an implicit or undocumented version.

```text

```

The exact representation is decided in this phase.


# 9. Why Version 1 Is Explicit

Versioning is not primarily about having multiple API versions today.

It creates a compatibility boundary.

Conceptually:

```text
Current clients
      ↓
    API v1
      ↓
Laravel domain
```

A future breaking redesign can become:

```text
API v1
API v2
```

without requiring all clients to update simultaneously.

---

# 10. Define What "Breaking Change" Means

Create an explicit list.

A breaking change is any API change that can reasonably cause an existing supported client to stop functioning correctly.

Examples:

```text
Removing a resource
Removing a required response field
Changing a field's meaning
Changing a required request field
Changing a value type incompatibly
Changing allowed enum/state values in a way old clients cannot handle
Changing authentication requirements incompatibly
Changing resource semantics
Changing endpoint behavior incompatibly
```

Document these as breaking.

---

# 11. Define Non-Breaking Changes

Examples:

```text
Adding an optional response field
Adding a new optional request field
Adding a new resource
Adding a new endpoint
Adding a new filter
Adding a new sort option
Adding a new optional relationship
```

However, be careful.

An apparently additive change may still break poorly designed clients.

For example:

```text
Adding a new enum value
```

can break clients that assume an exhaustive enumeration.

Therefore define special rules for extensible values.

---

# 12. Enum and State Compatibility

This is particularly important for your system because it contains:

```text
product types
order statuses
payment states
fulfillment types
request states
enquiry states
roles
```

Do not assume clients will always tolerate newly added enum values.

Define a versioning policy such as:

> Clients must treat unknown non-critical enum values safely unless the contract explicitly defines the value set as closed.

Later API contracts must state whether an enumeration is:

```text
OPEN/EXTENSIBLE
or
CLOSED
```

Do not decide all individual enum behaviors in this phase.

---

# 13. Response Compatibility

Define a general rule:

> Existing fields must not silently change meaning within the same major API version.

For example:

Version 1 payload:

```json
{
  "price": 1250000
}
```

must not later become within the same `v1` contract (breaking type change):

```json
{
  "price": "1,250,000 TZS"
}
```

Similarly, changing:

```text
price = total product price
```

to:

```text
price = discounted price
```

without explicitly documenting the semantic change is breaking.

---

# 14. Request Compatibility

Within the same API version:

* do not make an existing optional field suddenly required;
* do not remove a previously accepted request field;
* do not change the semantic meaning of an existing accepted value;
* do not unexpectedly narrow accepted values.

A request contract must remain stable for supported clients.

---

# 15. Resource Compatibility

Within `v1`, do not silently change a resource's fundamental identity or responsibility.

For example:

```text
Product
```

must continue to represent the same business concept defined in earlier phases.

Do not repurpose:

```text
Product
```

into:

```text
Product + manufacturing job + supplier record
```

without a deliberate versioning decision.

---

# 16. API Version vs Application Version

Keep these separate.

```text
API Version
→ v1
```

is not necessarily the same as:

```text
Flutter App Version
→ 1.8.3

Website Release
→ 2026.08
```

A Flutter update should not automatically require a new API major version.

Likewise:

```text
Website deployment
```

should not automatically change:

```text
API v1
```

---

# 17. Client Compatibility

The API serves multiple independent clients:

```text
Next.js website
Flutter mobile app
Admin application
```

A versioning policy must assume they may not update simultaneously.

Example:

```text
Flutter v1.4
Next.js release A
Admin release B
```

may all communicate with:

```text
API v1
```

Therefore:

> Do not make breaking API changes merely because one client has already been updated.

---

# 18. Mobile-Specific Compatibility

Flutter applications have a special consideration:

A user may keep an older version of the mobile app installed for a significant period.

Therefore API versioning must not assume:

```text
all mobile users upgrade immediately
```

For supported versions, document an explicit compatibility period later in the lifecycle policy.

Do not invent a fixed number of months in this phase unless already approved.

---

# 19. Website Compatibility

The Next.js website can often be deployed quickly compared with mobile clients.

However, do not assume that because the website is controlled by the project team, all API changes can be breaking.

The website and admin application still depend on the API contract.

---

# 20. Admin Compatibility

The admin application is also a client of the API.

Do not allow internal/admin APIs to bypass the same versioning discipline simply because the application is "internal."

Admin may have different access privileges but should still consume documented API contracts.

---

# 21. Internal vs Public APIs

Distinguish:

```text
Public application API
Internal backend mechanisms
```

Not every Laravel internal service is an API.

Versioning applies to APIs intended for client consumption.

For example:

```text
Laravel Action
Laravel Service
Repository
Database
```

do not need URL versioning merely because their implementation changes.

---

# 22. Version Scope

Define what the version applies to.

Recommended baseline:

```text
API contract version
```

rather than:

```text
database version
Laravel version
frontend version
```

This means a database migration does not necessarily mean:

```text
v2
```

A Laravel internal refactor does not necessarily mean:

```text
v2
```

Only externally observable contract changes matter.

---

# 23. Major vs Minor Changes

Establish semantic policy for API evolution.

Recommended conceptual model:

```text
v1
```

represents the major compatibility boundary.

Within v1:

```text
compatible additions
clarifications
bug fixes
```

may occur without changing the major version.

A breaking contract change requires:

```text
v2
```

Do not create artificial public URLs such as:

```text
/v1.1/
/v1.2/
/v1.3/
```

unless a later requirement proves this necessary.

---

# 24. Deprecation Policy

Define how an API feature becomes deprecated.

A deprecated resource/field/behavior should have:

```text
deprecation notice
reason
replacement
support expectation
removal policy
```

Do not immediately remove a deprecated feature.

For example:

```text
v1 field
   ↓
Deprecated
   ↓
Replacement documented
   ↓
Migration period
   ↓
Removal only through approved version transition
```

---

# 25. Deprecation vs Removal

Document:

```text
DEPRECATION
≠
REMOVAL
```

Deprecation means:

> Existing clients should migrate away, but the feature still exists.

Removal means:

> The feature no longer exists in the supported contract.

Removal of a previously supported feature is normally breaking and requires appropriate versioning.

---

# 26. Version Sunset

Define the concept of API sunset.

A future version may eventually be:

```text
ACTIVE
DEPRECATED
SUNSET
```

Do not define actual sunset dates for v1 yet.

The purpose is to establish the lifecycle concept.

---

# 27. Long-Lived Mobile Clients

Create an explicit rule:

> Before retiring a version, verify the active mobile-client versions and their API compatibility.

Do not sunset an API version solely because the latest mobile build no longer uses it.

---

# 28. Version Negotiation

Evaluate whether the API should support clients requesting a version dynamically.

For Version 1, prefer simplicity.

Do not introduce complex version negotiation unless there is a demonstrated requirement.

The versioning strategy should be obvious from the request.

---

# 29. Documentation Versioning

API documentation must carry the API version.

For example:

```text
API Documentation
Version: v1
```

Future:

```text
API Documentation
Version: v2
```

Do not let documentation become ambiguous when multiple versions coexist.

---

# 30. OpenAPI Versioning

The OpenAPI document must identify the API version clearly.

The OpenAPI specification itself has a version.

That is different from your API contract version.

Distinguish:

```text
OpenAPI specification version
API contract version
```

Do not confuse them.

---

# 31. Error Contract Compatibility

Error structures are part of the public API contract.

Once the error envelope is established later, clients may depend on it.

Therefore:

```text
error structure
error code
message semantics
validation format
```

must follow the same compatibility rules.

Do not allow error responses to change arbitrarily within a supported API version.

---

# 32. Authentication Compatibility

Authentication behavior is also part of the API contract.

A future authentication change must not unexpectedly invalidate supported clients.

However, authentication implementation details remain deferred to:

```text
Phase 1.21+ authentication contract work
```

or the corresponding authentication phase in the current roadmap.

This phase only establishes versioning implications.

---

# 33. Authorization Compatibility

Authorization behavior can also produce breaking changes.

Example:

```text
A customer could previously access resource X.
```

Changing that behavior may break the customer application.

Therefore authorization changes must be reviewed as potential contract changes.

Detailed authorization remains later work.

---

# 34. Endpoint URL Compatibility

Once endpoints are defined in later phases, the following become part of the versioned contract:

```text
path
method
request format
response format
authentication requirement
error behavior
```

Changing these incompatibly is a breaking change.

Do not define those details yet.

---

# 35. Versioning and Caching

If URL-based versioning is selected, the version becomes naturally visible to:

```text
HTTP caches
CDNs
logs
monitoring
developer tools
```

This is operationally valuable.

Document this as a consideration when evaluating the strategy.

Do not configure CDN caching yet.

---

# 36. Versioning and SEO

The API version must not become part of public SEO URLs such as:

```text
/products/modern-sofa
```

The public website URL structure and internal API versioning are separate concerns.

For example:

```text
SEO URL:
https://example.com/products/modern-sofa

Internal data request:
https://api.example.com/api/v1/products/modern-sofa
```

The exact domains are not being defined here.

---

# 37. Versioning and Flutter Deep Links

Do not place API versioning concepts into customer-facing mobile deep links.

A deep link is a product/application navigation concern.

API versioning is a backend contract concern.

Keep these independent.

# 41. Versioning Governance

Define who/what controls version changes.

At minimum:

```text
API contract changes
→ documented review

Breaking changes
→ explicit approval

Version freeze
→ documented baseline
```

Do not permit an individual developer to silently change the API contract because it is convenient for implementation.

---

# 42. API Version Ownership

Assign conceptual responsibility:

```text
API Contract
→ Engineering/API architecture

Business behavior
→ Approved business/domain rules

Implementation
→ Laravel backend

Clients
→ Next.js / Flutter / Admin
```

No single frontend should unilaterally redefine the shared API.

---

# 43. Version Change Process

Define:

```text
Proposed change
      ↓
Determine breaking/non-breaking
      ↓
Impact analysis
      ↓
Client compatibility review
      ↓
Approval
      ↓
Documentation update
      ↓
Implementation
      ↓
Testing
      ↓
Release
```

For breaking changes:

```text
Proposed change
      ↓
Create new major API version
      ↓
Migration strategy
      ↓
Parallel support where required
      ↓
Client migration
      ↓
Deprecation
      ↓
Sunset
```

---

# 44. Version 1 Freeze Rule

Once the Version 1 API contract is later frozen, changes must obey the versioning policy.

Do not treat:

```text
"it's only one small field"
```

as a reason to bypass contract governance.

Every change must be classified.

---

# 45. No Premature v2

Do not design v2 now.

Only define:

```text
how v2 would be introduced
```

if a future breaking contract becomes necessary.

Do not invent hypothetical v2 endpoints.
